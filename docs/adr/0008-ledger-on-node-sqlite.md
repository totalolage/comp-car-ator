# The Ledger is one SQLite file accessed through `node:sqlite`, with Resolution at snapshot time

The Ledger is a single SQLite file, opened with Node's built-in `node:sqlite` (`DatabaseSync`), with append-only migrations tracked in a `meta` table. A file is the natural unit to carry between ephemeral ingest runs as a release asset, and SQLite gives transactions, indexes and SQL for the read model without a server. We chose `node:sqlite` over `better-sqlite3` because it ships with Node 24: no native module to compile or download on home runners, CI and contributors' machines, and the same synchronous API shape. Tests open `:memory:`, which is why the Ledger has no port (a local-substitutable dependency; see ADR 0001).

Listings are matched to catalog Variants when the Ledger produces a snapshot, not when an Observation is recorded. The catalog changes monthly and the Resolver will keep improving (Wave 1 stream 11); resolving at snapshot time means every publish uses the latest catalog and Resolver, with no stored matches to migrate. The cost is re-resolving every listing per publish, which is in-process and cheap at the expected ~150k listings. Because the model a listing belongs to exists only in the snapshot, `snapshot().listings(ids)` reads given listings back by id: the Publisher makes one pass to group ids by model and then reads one model at a time, so it never holds every listing (ADR 0012, Scale). The alternative, storing each listing's Resolution so SQL can group by model, would bring back the stored matches this decision avoids.

## Consequences

- A failed Observation iterator still commits its accepted prefix and finished-slice absence inference. `record` rejects with `RunFailedError`, whose `cause` is the original failure and whose `summary` counts that durable work. The error identity changes; callers needing the original use `cause`. Storage, processing and finalization errors remain fatal and carry no publishable summary. Summaries count new misses from SQLite's affected rows and all rejections separately from the capped rejection examples. A failed full run reports `census: "incomplete"`, never a completed census.
- One writer at a time; the ingest job owns the file.
- Never edit a shipped migration; append a new one. A Ledger newer than the code refuses to open.
- Data a Source recorded wrong is fixed in the Source and, for what the Ledger already holds, by a migration: a daily run skips known listings, and even a Census re-sighting leaves the wrong price in history. Such a migration names the rows it changes, each confirmed against the site (not inferred from the data itself), changes only what the site's evidence covers (a price is relabelled only at the amount the site showed, since one at another amount may have been right; an earlier price that happened to equal it cannot be told apart and is relabelled too), and does not change prices recorded since the fix. The exception is a label the adapter's own code wrote only in a case that live samples show was wrong: it is relabelled across the Source without naming rows. The correction only relabels (a currency or a price basis) and never deletes history points, so it is safe whenever the next release opens the Ledger. The Data release before that one is its backup. Migration 4 relabels TipCars prices recorded as CZK at the EUR amount the listing showed. Migration 5 relabels as gross the Sauto prices recorded as net: the adapter wrote net only for a seller who priced without VAT, and the amount it stored was the headline with VAT added (20 of 20 live samples).
- Census bookkeeping is not data a Source recorded, so a migration may derive it from the data: migration 6 files each full run under its census (`runs.census`, the census's first full run) and gives Bazoš and TipCars listings recorded before their adapters named a slice the one each adapter names (ADR 0003, Absence per finished slice). A slice derived wrong can at worst count a live listing missed in a slice it is not in, which a sighting anywhere in the census undoes, as for a listing that moved.
- If `node:sqlite` changes incompatibly before it is marked stable, swapping to `better-sqlite3` touches only `packages/ledger`.
