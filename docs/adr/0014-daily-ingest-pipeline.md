# The daily ingest harvests Sources in parallel jobs into Run logs, and one job records them and cuts a Data release

The ingest workflow in `totalolage/comp-car-ator-ingest` (ADR 0007) fires once a day on the ephemeral home runners. A `plan` job picks the base Data release (the newest) and the harvests due; one `harvest` job per Source restores the base Ledger only for its Checkpoint and writes its Run to a Run log; a single `release` job restores the same base Ledger, records every Run log into it oldest first, publishes the Bundle, uploads the new Data release and calls the Vercel deploy hook. Runners keep no disk between jobs, so Data releases of this public repo are the only state.

Run logs replay through `Ledger.record`: a harvest that failed or a log cut short ends by throwing, so the Ledger keeps what was recorded (and each SliceDone) and marks the Run failed, exactly as an in-process failed Run. The only difference from recording while harvesting is that a harvest's Checkpoint does not see the Run's own Observations, which can only make an incremental Run fetch more, never less. We considered one job running every Source in turn (simpler, but one slow or blocked site holds up the rest and the runners' three slots sit idle) and one Ledger per job merged afterwards (needs a Ledger merge, a contract change for no gain).

A Data release is tagged `data-<UTC yyyymmdd-hhmmss>` and carries `ledger.sqlite.zst` (zstd, `node:zlib`), `bundle.json.gz` (`packBundle` in `@cca/bundle/node`: the Bundle's files as one gzipped JSON document) and `manifest.json` (sha256 and size of both assets, the base it was built on, the commit of this repo it ran, each Run's outcome, and each Source's last applied Census). The `ReleaseStore` seam in `apps/ingest` has two adapters: GitHub Releases (the workflow) and a local directory (local runs and tests).

## Consequences

- A Data release becomes visible only when complete: on GitHub it is a draft until every asset is uploaded, then one update publishes it and marks it the repo's latest release (in a directory, a rename). Any failure before that leaves the previous Data release as the latest. Drafts left by a crashed run are deleted by the next release.
- Run logs are recorded only onto the base they were harvested against, and only once: `release` refuses when the newest Data release is no longer the base. Re-running a failed `release` job of the same workflow run is safe while nothing newer was released. The check runs just before the upload, so it relies on one writer: only the ingest workflow creates Data releases, and its concurrency group keeps two ingests from overlapping.
- `restore` and `release` refuse to start an empty Ledger unless `--init` is passed (only for the very first run), so a listing error can never replace the Ledger with an empty one. Restores check the Ledger asset's sha256 against the manifest.
- The newest 14 Data releases are kept; older ones and their tags are deleted.
- The site build downloads `https://github.com/totalolage/comp-car-ator/releases/latest/download/bundle.json.gz` (no API call, no token, no rate limit) on production builds (ADR 0006). This repo's "latest release" therefore belongs to the data: a code release, if ever made, must be created with `make_latest: false`.
- Schedule (`apps/ingest/src/schedule.ts`): listing Sources run incrementally each day and take a Census on Sundays; ČNB runs incrementally each day; catalog and register Sources take only a Census, on the 1st of the month. A Census is due whenever the Source has had none since its latest scheduled day, so a failed or skipped Census (GitHub may drop scheduled events) runs again the next day. Add a line there for a Source that differs from the listing default.
- The private repo holds two secrets: `DATA_RELEASE_TOKEN` (fine-grained PAT for this repo only, Contents read and write) and `VERCEL_DEPLOY_HOOK` (production branch `main`). Neither appears in this repo.
