# The daily ingest harvests Sources in parallel jobs into Run logs, and one job records them and cuts a Data release

The ingest workflow in `totalolage/comp-car-ator-ingest` (ADR 0007) fires once a day on the ephemeral home runners. A `plan` job picks the base Data release (the newest) and the harvests due; one `harvest` job per Source restores the base Ledger only for its Checkpoint and writes its Run to a Run log; a single `release` job restores the same base Ledger, records every Run log into it oldest first, publishes the Bundle, uploads the new Data release and calls the Vercel deploy hook. Runners keep no disk between jobs, so Data releases, kept as GitHub Releases of the private ingest repo, are the only state.

Run logs replay through `Ledger.record`: a harvest that failed or a log cut short ends by throwing, so the Ledger keeps what was recorded (and each SliceDone) and marks the Run failed, exactly as an in-process failed Run. The only difference from recording while harvesting is that a harvest's Checkpoint does not see the Run's own Observations, which can only make an incremental Run fetch more, never less. We considered one job running every Source in turn (simpler, but one slow or blocked site holds up the rest and the runners' three slots sit idle) and one Ledger per job merged afterwards (needs a Ledger merge, a contract change for no gain).

A Data release is tagged `data-<UTC yyyymmdd-hhmmss>` and carries `ledger.sqlite.zst` (zstd, `node:zlib`), `bundle.json.gz` (`packBundle` in `@cca/bundle/node`: the Bundle's files as one gzipped JSON document, one file per line, compressed to disk as the Publisher produces them; a full Bundle is longer than the longest string V8 holds, so neither side builds the document as one string) and `manifest.json` (sha256 and size of both assets, the base it was built on, the commit of this repo it ran, each Run's outcome, and each Source's last Census taken). The `ReleaseStore` seam in `apps/ingest` has two adapters: GitHub Releases (the workflow) and a local directory (local runs and tests).

## Consequences

- A Data release becomes visible only when complete: on GitHub it is a draft until every asset is uploaded, then one update publishes it and marks it the repo's latest release (in a directory, a rename). Any failure before that leaves the previous Data release as the latest. Drafts left by a crashed run are deleted by the next release.
- A failed harvest and a failed release are different: a failed harvest still goes into the new Data release as a failed Run, with what it recorded and its finished Slices (that progress is how a Census resumes), while a failed `release` publishes nothing and the latest Data release stays as it was.
- Failed Runs retain their partial RunSummary in the manifest, release notes and warning log alongside the error: per-kind accepted counts, new listings, price changes, Gone, new misses and total rejected observations. `incomplete` full runs cannot advance `lastCensus`. Truncated logs retain the same safe partial-run behavior; malformed JSON, file-read errors and Ledger storage errors abort the release rather than being labelled failed harvests.
- Run logs are recorded only onto the base they were harvested against, and only once: `release` refuses when the newest Data release is no longer the base. `plan` prints the base, and `restore` and `release` take it as `--base` (required for `release`); on the first run it is `--base ""`, which refuses once any Data release exists, so a retried first run cannot record its logs onto a Ledger released after them. Re-running a failed `release` job of the same workflow run is safe while nothing newer was released. The check runs just before the upload, so it relies on one writer: only the ingest workflow creates Data releases, and its concurrency group keeps two ingests from overlapping.
- `restore` and `release` refuse to start an empty Ledger unless `--init` is passed (only for the very first run), so a listing error can never replace the Ledger with an empty one. Restores check the Ledger asset's sha256 against the manifest.
- The newest 14 Data releases are kept; older ones and their tags are deleted.
- Data releases are private: the Ledger (full listing and price history) and the release archive stay in the private repo. The Bundle the site serves is public by nature, since the site is static. Production builds download the latest Data release's Bundle through the GitHub API with `BUNDLE_TOKEN`, a read-only fine-grained PAT for the ingest repo kept as a sensitive, Production-only Vercel environment variable, and check it against the manifest's sha256 (ADR 0006). Previews build from the sample Bundle and never see the token.
- Schedule (`apps/ingest/src/schedule.ts`): listing Sources run incrementally each day and take a Census on Sundays; ČNB runs incrementally each day; catalog and register Sources take only a Census, on the 1st of the month. A Census is due whenever the Source has had none since its latest scheduled day, so a failed or skipped Census (GitHub may drop scheduled events) runs again the next day. A Census that ended with rejections still counts as taken for the schedule: it marked nothing gone beyond the slices it finished cleanly (ADR 0003), but retrying it daily would run a Source with one persistent bad listing in full every day. Add a line there for a Source that differs from the listing default.
- A Census can take several days. Sauto reads one detail page per listing at about 1 request/s, roughly 30–40 hours for the whole scope. On Census days a daily Source runs incremental first, then full in the same job, with separate Run logs recorded oldest first. Incremental gets at most an hour, or the Source's `catchUpMinutes` allocation: Bazoš has 150 minutes and TipCars 120. Full gets the remainder of `--max-minutes`, even if incremental fails. The source request bounds below normally let incremental finish sooner. Incremental sees new listings in slices the resumed Census skips, and any sighting during a Census prevents that listing being counted missed. A complete full run ends the Census; stalled-Census restart rules remain in ADR 0003. We considered alternating incremental and full days, which halves Census progress, and separate jobs, which hit one site concurrently.
- TipCars incremental allows 100 Source HTTP calls per list for newest listings, including unknown new/demo detail reads, then 2,000 calls for the known-price sweep. Run 40831796333 completed its two heads after 7 used pages and 2 new pages, but the sweep timed out after 3,244 successful unique page results. Median page spacing was 2.126 seconds and p90 was 2.829, above the earlier 1.7-second estimate. At that p90 the new maximum 2,200 calls takes about 104 minutes within its unchanged 120-minute allocation. This is a request bound, not a wall-clock guarantee: transport retries and slow responses can still time out. The sweep keeps the existing daily rotation over shares of nine tenths of its cap. The roughly 3,400 current pages take two days while counts stay stable and Runs complete. Failed days, changing page counts and offset movement can delay individual listings longer. Head caps defer unknown candidates; full remains responsible for complete coverage. We chose smaller request allocations over a larger runner deadline.
- Bazoš incremental permits 100 Source HTTP calls per category, including list rereads, overlap backsteps and details that later prove out of scope. Its 25 default categories therefore use at most 2,500 logical calls. An exhausted category logs its interrupted URL, cutoff day and calls used, then continues to later categories without SliceDone. This is best-effort freshness: after a capped complete incremental advances `lastRunAt`, unvisited older candidates may wait for full. Transport retries and slow responses can still exhaust the runner deadline. Full high-water count reconciliation remains strict. The historical Ford short pages could not be reproduced from current responses, so a moving count still fails with page and reconciliation diagnostics instead of forgiving missing listings.
- Sauto incremental's 2,400-request allowance counts search and detail calls together. The failed run made 963 search calls and received 2,271 distinct detail responses before 60 minutes; the earlier detail-only allowance omitted about 16 minutes of search work. At the observed throughput 2,400 calls take about 44 minutes, without guaranteeing wall time. Unknown details stream per search page in `sorting_date` order, after that page's known-price sightings; eligibility still includes old drafts published late. Exhausting the allowance fails explicitly, preserving the previous `lastRunAt`. A first run has only its rolling one-day window, and a continually moving or oversized search prefix can still delay older eligible candidates. Full traversal and absence rules are unchanged.
- The experimental `mobile-de` Source is manual only (ADR 0015).
- The workflow writes Data releases to its own repo with its built-in `GITHUB_TOKEN` (`contents: write` on the `release` job only); its one secret is `VERCEL_DEPLOY_HOOK` (production branch `main`). Neither token appears in this repo.
- A harvest stops itself after `--max-minutes` (330 in the workflow, under the 360-minute job limit) and is recorded as a failed Run (the runner checks the deadline after each Observation and before ending the log as complete, even when the Source never looks at its signal), so a Census too long for one day resumes from its finished Slices the next day. Self-hosted jobs may run up to 5 days, but we keep the daily bound: three runner slots took 11 hours of wall time for the first Census, longer jobs would push a run past the next day's, and the concurrency group keeps at most one run pending (a newer pending run replaces it), so an overrun drops a day's release instead of queueing it.
- Harvests run without the raw response cache (`--cache`). It serves every repeated request from disk, so a slice's second pass or a recount re-read the first read and could never catch the listings that moved under the walk: in the first Census, TipCars, Sauto, Bazoš and AutoScout24 slices stayed short by the same count on every pass, never finished, and kept their Census from ever ending (a live re-read of a TipCars slice reported short that way finished in one pass).
