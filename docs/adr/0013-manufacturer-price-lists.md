# Manufacturer price lists: read the importers' PDFs, withdraw from the Ledger's editions

New prices come from the Czech importers' own price lists (ceníky), one Source per brand: `skoda-pricelist` and `vw-pricelist`. Both are thin brand adapters over one price-list module (`packages/sources/src/pricelist/`), which owns fetching, PDF text extraction (unpdf, pure JS), turning rows into `ListPrice`, rejecting malformed rows and withdrawing Offers. A brand adapter says where its lists are (`models`) and how one reads (`read`). The two brands vary in exactly that, so the split is a seam with two adapters; Toyota, Hyundai or Kia would be a third.

## Decisions

- **The PDF is the authority.** It is the only public document that prices every Offer and states the day its prices start ("Platnost od"). The brands' configurator APIs (Škoda CC3, VW's Porsche Informatik CC) publish codes, model years and "from" prices per trim, but no per-Offer price and no date, so an edition's `validFrom` would have to be guessed. Škoda's configurator still supplies two fields its lists leave out: model year and body, per model name.
- **Body, per model name, as the brand names it.** Neither brand's lists print a body, and without one a row fits every register Variant that differs only in body (Touran, Octavia). Each Source states the body the brand's own site files the model under, not the register's code for it; the Resolver bridges the two taxonomies. Škoda: the configurator's model groups (Hatchback, Liftback, Kombi, SUV; a liftback is a hatchback by shape). VW: the categories its model overview (`/modely`) files each model on sale under (Hatchback, Kombi, Limuzíny, SUV), read from the page's Next.js flight data; so the ID.7, a liftback VW files as Limuzíny, states sedan, while Škoda's Liftback states hatchback. Models still listed but no longer configurable carry no category there; a two-entry table names their one body (Touran MPV, Touareg SUV). A model the site files under two bodies leaves body out, table or not, and so does one filed under none that the table lacks.
- **Offer codes.** VW rows carry the manufacturer's sales code (`CT1CPT03`), which is the code. Škoda rows carry none, so the code is built from what the row prices: model (with Combi/Coupé), engine, fuel, gearbox, drive and trim line (`octavia-combi.2-0-tdi-110-kw.diesel.a.fwd.selection`). Model year stays out of both: VW's file names show it only sometimes, and an Offer must keep its ref across editions. A ref is `<model key>/<code>`, so the Ledger's editions say which model's lists an Offer came from.
- **Withdrawal.** Manufacturers keep no archive of earlier editions, so the Source compares the current lists with `checkpoint.offersInForce()` (ADR 0003). Only full runs withdraw, and only Offers of a model whose every list was fetched and read without a rejected row. An Offer ends the day before the first of the model's current lists issued after its edition started. While no current list is newer than its edition (a list reissued under the same date without the row), it stays in force: such a list is no evidence of when the Offer ended, and the run day would date the end by when ingest happened to run. For a model with one list the end day is exact; with several (VW action lists) it is an estimate, since rows carry no list of origin. A model that left the brand's index ends the day before the run, provided the index read whole (no link that looks like a price list without a readable model) and every listed model read cleanly. A model listed without lists (VW's Ceníky page 404s) is neither read nor withdrawn. Readers reject what they cannot key rather than skip it, anywhere in the document, since the Offers of a table they did not read would look dropped: a table header that names known columns but does not read; on Škoda lists a price no row read on a grid page, or on any page that names an engine as a grid row does ("1,5 TSI/110 kW"); on VW lists a row priced without a sales code, or a priced sales-code row outside the tables read. Pages that price options and packages name neither engines that way nor sales codes, so they stay out. Two lists of one model pricing the same Offer on the same day must agree, or neither price is recorded; on different days they are two editions. Incremental runs read the same lists and never withdraw.
- **Failure.** An unreadable list (not a PDF, no date, a layout that yields no row) is skipped with a warning and withdraws nothing; the run fails only when no list of the brand reads, which is what a redesign looks like. Blocked or unreachable Http fails the run as for any Source.

## Alternatives

- **Configurator JSON as the price source.** Machine-readable, but undated and incomplete per Offer; rejected as the authority, kept for model year and body.
- **The Ledger infers withdrawals** (Offers a complete full run did not see end), as it does for listings. Rejected in ADR 0003: the Ledger cannot tell which document an Offer came from, so one unreadable PDF would retire a whole model.
- **pdftotext (poppler) for extraction.** Simpler layout output, but a system dependency on every runner; unpdf's positioned text plus column assignment by header position covers both brands' tables.
- **A curated body table for every VW model.** Simplest to read, but every new model would wait for a code change; the overview states the body of each model on sale, so the table covers only what it leaves out.
- **Register body codes in the Sources.** The register files many hatchbacks as wagons or sedans (Golf 8, Octavia liftback); stating its code would make each Source repeat the register's taxonomy. Kept in the Resolver, which bridges stated bodies to the register's (ADR 0002: a Golf or ID.3 hatchback reaches the register's wagon only in the generations its aliases name).
- **VW Group OKAPI.** Official, but needs company registration and approval; not available to this project.
