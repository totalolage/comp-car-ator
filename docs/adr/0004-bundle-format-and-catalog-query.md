# Bundle owns the format (writer + reader); the catalog query engine owns querying

The published data is a Bundle: a directory of static files written by the Publisher and read by the website. One module, `@cca/bundle`, owns both sides of the format: the decoded document types (`BundleContent` = manifest + catalog index + one model file per Model), a pure writer `encodeBundle(content) → files` with a streaming form `encodeBundleFiles(models, index)` (model files as they come, then the catalog and manifest that summarise them; the Publisher uses it so a Bundle never has to sit in memory decoded, ADR 0012), and a reader `openBundle(loader)` with `catalog()` and `model(id)`. The catalog query engine, `@cca/catalog`, sits on the reader: `openCatalog(loader)` loads the manifest and catalog index once, then `query(filters, sort, page)` is synchronous and returns rows plus facet counts, and `model(id)` returns a view whose `listings(query)` runs the same facet engine over that model's listing index and whose `rows(entries)` loads the full rows of some of them. `openModel(loader, id)` gives a model page the same view without the catalog index. File names, sharding and encoding are private to Bundle, so the Publisher and the web never change when the layout does.

## Format v3

- `manifest.json`: format version, publish time, FX rates used, source run times, counts. The reader refuses any other format version (`BundleFormatError`); bump `BUNDLE_FORMAT` for any change an older reader cannot read.
- `catalog.json`: makes, models, and one row per Variant with specs, new price (with its source: manufacturer list or Czech dealer Listings) and used-price statistics (count, p10/median/p90, also per Market; no quantiles under 3 Listings, ADR 0012). Loaded once by the browser; everything the facet rail needs.
- `models/<make>/<model>/index.json`: the model's listing index. Generations, price statistics as a sparse cube of cells (Variant or whole model × Market × Condition × year × odometer band, with "all" marginals; cells under 3 Listings left out), a weekly median-price series per Market, and one `ListingEntry` per Listing (active, and gone in the last 30 days): only the fields the listing filters, sorts and statistics read (Variant, Market, Source, Condition, body, fuel, gearbox, year, odometer, CZK price, landed total, power, days on market, first seen, gone, excluded). Entries are stored active and kept first, then cheapest landed price first, so the page a model opens on sits in the first rows file.
- `models/<make>/<model>/<n>.json`: the full `ListingRow`s (title, URL, price as shown, landed-price lines, photos, price history, seller, location) of entries `32n` to `32n + 31` in index order. `rows(entries)` loads only the files those entries sit in, each once.

The writer still takes whole `ModelFile`s, so the Publisher does not see the split; the reader returns a `ModelIndex` (the model file with entries instead of rows, plus `rows`). The catalog engine filters, counts, sorts and computes statistics on entries; a table loads rows for the page it shows.

JSON, with the long row lists (catalog Variants, a model's Listings and price cells) stored column-wise: one array per field, strings dictionary-coded when they repeat, fields that most rows lack stored sparsely, nested objects and arrays as nested columns (`packages/bundle/src/columns.ts`). The reader decodes them back into the same documents, so the encoding stays invisible to the catalog query engine. At 50k Variants with full specs this keeps `catalog.json` at 10.28 MiB raw and 1.44 MiB gzip (measured, ADR 0012), against 25-40 MB as plain rows. The codec is generic over JSON rather than written per field, so a new field in a row type needs no encoding change.

v3 (2026-10-28) split each model file in two. With the first full censuses (810k published Listings) the largest model file was 2.4 MB gzip, a model page loaded it and the 0.87 MB `catalog.json` on hydration, and the staged Bundle made the deployment 0.9 GB. Photos were over half of a model file's compressed bytes, URLs and ids another third, and a page shows 25 rows at a time. Measured on the real Bundle: the listing index is 88 kB gzip for the Opel Corsa (13,774 Listings) and 121 kB for the largest, the Škoda Octavia (14,366); most models' are a few kB, and a rows file is about 4-5 kB. A non-default sort or a selective filter scatters the shown rows over up to one rows file each (sorting the Corsa's German Listings by year loads 12 files, about 53 kB); each "show more" can add up to 50 more. Files of 32 rows were chosen against twice the files at 16 rows or an index two to three times larger with titles and prices in it.

The website stores every Bundle file gzipped as `<path>.gz` (`writeBundleFiles(dir, files, { gzip: true })`) and reads it with `fetchLoader(url, { gzip: true })`, which inflates with the browser's `DecompressionStream` unless the host already did. The deployment then holds the compressed bytes. The committed sample Bundle and `ingest publish --out` stay plain JSON, and `fsLoader` reads either.

Each rows file carries a stamp of its index (a hash of the Listing ids in index order and their entries). A page left open across a deploy still holds the old index, and the new rows files could put other Listings, or other prices, at its positions; the reader rejects them with `BundleChangedError` and the model page opens the index again on its next use.

`unpackBundle` rewrites a format-2 archive (one file per model) into format 3 as it reads it, so the web build stages the Data release published before this change; the browser reader reads format 3 only. A commit from before format 3 fails its build on a format-3 release (`BundleFormatError`), so the previous deployment stays up (ADR 0006).

v2 (Wave 1 stream 12) replaced v1's model-level `byYear`/`byOdometerBand` medians, `min/p25/median/p75/max` quantiles and pooled daily history: the catalog needs per-Variant, per-Market, robust statistics, and pooling Czech gross prices with German net ones in one median hid the difference a buyer cares about. The Publisher's rules for these numbers (outliers, new-price precedence, compaction) are in ADR 0012.

## Facet semantics

Values inside one facet are OR-ed and facets are AND-ed. Counts are disjunctive: each facet's counts apply every active filter except its own, so the rail always shows what another choice would yield (the McMaster-Carr behaviour).

Listing-level filters on the catalog (market, source, used price, odometer) must hold together: each Variant row carries its active used listings split into (market, source) groups with price, odometer and year ranges, and a Variant matches when one group satisfies all of them. Without the groups, a Variant with Czech listings on Sauto and German ones on AutoScout24 would wrongly match "Germany + Sauto" (found by the envoy-peer review). Inside a group, price and odometer are compared by range overlap, so the catalog stays an approximation; exact per-listing filtering (and landed price) happens in `model(id).listings(query)`. The query engine expands each Variant into one row per group and counts distinct Variants.

## Considered options (design it twice)

- **B1, chosen: Bundle = format (types + writer + reader), catalog = query engine on the reader.** Format locality in one module, query locality in another; the decoded types are a shared contract that the Astro build, the islands and the Publisher all use.
- **B2: merge reader and query engine into one module.** The encoding could be co-designed with querying (precomputed facet bitsets, columnar scans), but the Publisher (Node) would depend on the query engine, and pages that just render a model file would have to go through query calls. Kept as a later option: the writer may emit extra precomputed indexes that the query engine consumes, still behind Bundle.
- **B3: publish the Ledger read model as SQLite and query it in the browser (sql.js + HTTP range requests).** One format and SQL for facets, but ~1 MB of wasm before first paint, awkward caching on static hosting, and the web would be coupled to the Ledger schema (no format locality at all). Rejected.
- **B4: pre-render every filter combination as static JSON.** Combinatorial explosion. Rejected.
- **B5: row iterators (`variants()`, `listings(modelId)`) instead of whole documents.** Streaming is pointless when the browser needs the whole catalog index in memory for instant faceting; more interface for no caller. Rejected.
- **B6 (v3): split a model file further, or not at all.** One file per model put megabytes on a popular model's page. Titles and prices in the index (214 kB gzip on Corsa) or URLs too (670 kB) let any page render without rows files, at the cost of the first fetch; rows files of 16 halve the bytes a scattered page loads but double the files (51k); a separate detail tier (photos, landed lines, history) fetched on expand saves about half of a scattered page again for a third kind of file. Kept the two-part split: the index answers every query, rows files answer what is shown.
- **Pre-compressed files (v3) vs plain JSON with fewer fields.** Dropping photos and ids still leaves over 300 MB raw; per-file gzip brings the whole Bundle to its compressed size without changing what a page can show. One photo instead of three would save another ~28% of rows-file bytes and stays a Publisher option (ADR 0012).

## Loader seam

`Loader = (path) => Promise<string | null>` has three adapters: `fetchLoader(baseUrl, { gzip })` in the browser, `fsLoader(dir)` at build time and in Node (`@cca/bundle/node`, plain or gzipped files), and `memoryLoader(files)` in tests, fed straight from `encodeBundle`. Three real adapters, so a real seam.
